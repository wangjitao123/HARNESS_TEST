# 交叉评审技能

## 功能描述

对多份产物进行交叉一致性检查，识别三类问题：
1. **冲突**：两份文档对同一事物有矛盾定义
2. **遗漏**：上游有需求但下游无对应实现
3. **越界**：下游有实现但上游无对应需求

适用于 stage-05 概要设计完成后，在进入开发阶段前确保各产物间的事实源对齐。

## 输入参数

| 参数名 | 类型 | 必填 | 描述 | 示例 |
|--------|------|------|------|------|
| project_name | string | 是 | 项目名称 | HIS系统 |
| prd_doc | string | 是 | PRD文档路径 | docs/需求分析/PRD-HIS系统.md |
| architecture_doc | string | 否 | 架构设计文档路径 | docs/概要设计/架构设计/架构设计文档-HIS系统.md |
| database_design_doc | string | 否 | 数据库设计文档路径 | docs/概要设计/数据库设计/数据库设计文档-HIS系统.md |
| api_design_doc | string | 否 | API设计文档路径 | docs/概要设计/架构设计/API设计.md |
| test_case_doc | string | 否 | 测试用例文档路径 | docs/需求理解/M01-门诊管理/M01-01-挂号管理/功能点清单.md |
| review_depth | string | 否 | 评审深度：quick/standard/deep，默认 standard | standard |
| output_dir | string | 否 | 评审报告输出目录，默认与PRD同目录 | docs/需求分析 |

## 使用示例

### 示例1：stage-05 后触发交叉评审

```bash
/cross-review --project_name "HIS系统" --prd_doc "docs/需求分析/PRD-HIS系统.md" --architecture_doc "docs/概要设计/架构设计/架构设计文档-HIS系统.md" --database_design_doc "docs/概要设计/数据库设计/数据库设计文档-HIS系统.md"
```

### 示例2：深度评审（含API和测试用例）

```bash
/cross-review --project_name "HIS系统" --prd_doc "docs/需求分析/PRD-HIS系统.md" --database_design_doc "docs/概要设计/数据库设计/数据库设计文档-HIS系统.md" --api_design_doc "docs/概要设计/架构设计/API设计.md" --test_case_doc "docs/需求理解/M01-门诊管理/M01-01-挂号管理/功能点清单.md" --review_depth "deep"
```

## 工作流程

1. **文档加载阶段**：加载所有提供的文档
   - 解析PRD，提取功能点列表、用户故事、验收标准
   - 解析架构设计，提取组件清单、模块划分
   - 解析数据库设计，提取表结构、字段、索引
   - 解析API设计，提取接口列表、请求/响应结构
   - 解析测试用例，提取用例清单、覆盖范围

2. **交叉检查阶段**：按交叉检查矩阵逐项检查
   - 需求↔数据库：每个功能点的数据实体是否都有对应表
   - 需求↔API：每个用户故事是否有对应API接口
   - 需求↔测试：每条验收标准是否有对应测试用例
   - 数据库↔API：API字段与数据库字段是否一致
   - 架构↔数据库：每个组件的数据存储是否已设计
   - 测试↔API：测试用例是否覆盖所有API

3. **冲突分析阶段**：识别冲突、遗漏、越界三类问题

4. **报告生成阶段**：生成交叉评审报告，含冲突矩阵、遗漏清单、越界检测、追溯覆盖率

## 交叉检查矩阵

| 检查项 | 源文档 | 目标文档 | 检查内容 | 严重程度 |
|--------|--------|----------|----------|----------|
| 需求↔数据库 | PRD功能点 | 数据库设计 | 每个功能点的数据实体是否都有对应表 | 🔴高 |
| 需求↔API | PRD用户故事 | API设计 | 每个用户故事是否有对应API接口 | 🔴高 |
| 需求↔测试 | PRD验收标准 | 测试用例 | 每条验收标准是否有对应测试用例 | 🔴高 |
| 数据库↔API | 数据库字段 | API请求/响应 | API字段与数据库字段类型、名称是否一致 | 🟠中 |
| 架构↔数据库 | 架构组件 | 数据库表 | 每个组件的数据存储是否已设计表结构 | 🟠中 |
| 测试↔API | 测试用例 | API接口 | 测试用例是否覆盖所有API | 🟠中 |
| PRD↔架构 | PRD模块划分 | 架构组件 | PRD中的每个模块是否有对应的架构组件 | 🟢低 |
| 数据库内部 | 表结构 | ER关系 | 外键关系是否合理，是否存在孤立表 | 🟢低 |

## 评审深度说明

| 深度 | 检查范围 | 适用场景 |
|------|---------|---------|
| quick | 仅需求↔数据库、需求↔API，只输出🔴高严重度问题 | 快速验证 |
| standard | 前6项检查，输出🔴+🟠问题 | 中等规模项目（默认） |
| deep | 全部8项检查 + 字段级比对，输出全部问题 | 复杂项目深度评审 |

## 产出物清单

| 文档名称 | 文件格式 | 存放路径 |
|---------|---------|---------|
| 交叉评审报告 | .md | {output_dir}/交叉评审报告-{project_name}-{timestamp}.md |

评审报告包含：评审概要、交叉检查统计、冲突问题清单、遗漏问题清单、越界问题清单、追溯覆盖率、评审结论。

## 评审结论分流

- **✅ 通过** → 进入下游阶段
- **⚠️ 不通过** → 列出冲突/遗漏/越界问题，引导用户返回上游修改后重新评审

## 注意事项

1. **至少提供PRD文档**：PRD是交叉评审的事实源，必须提供
2. **可选文档**：其他文档为可选，提供越多检查越全面
3. **不修改原文档**：评审只产出报告，不直接修改设计文档
4. **AI建议仅供参考**：每条问题的建议只是参考，用户有权否决
